S08 подключает тебя через `getattr`: `app.candidates.find_candidates`, `app.candidates.find_duplicate_candidates`, `app.matching.verify_matches`, `app.matching.confirm_loss` — имена держи ровно такими.

**Пишешь только в:** `backend/app/candidates.py`, `backend/app/matching.py`, `backend/app/prompts/verify_matches.md`, `backend/app/prompts/confirm_loss.md`, `backend/app/mocks/verify_matches/**`, `backend/app/mocks/confirm_loss/**`, `backend/app/mocks/embeddings/**`, `backend/tests/test_matching.py`.
**Не трогаешь:** `main.py`, `schemas.py`, `llm.py`, `llm_schemas.py`, `prebuilt/`, `pipeline.py`, `duplicates.py`, чужие модули и тесты, фронт. Новых зависимостей нет (numpy уже есть).

Задача: два модуля. `candidates.py` — гибридный поиск кандидатов, без статусов: `find_candidates(before: list[Function], after: list[Function], llm: LLM | None = None, k: int = 5) -> dict[str, list[Candidate]]` (для каждой функции «до» — до 5 кандидатов «после») и `find_duplicate_candidates(functions: list[Function], k: int = 5) -> list[tuple[Function, Function, float]]` (пары функций **разных** подразделений одной версии; S11 проверяет их своим `verify_duplicates`). `matching.py` — решение: `verify_matches(before: list[Function], after: list[Function], candidates: dict[str, list[Candidate]], llm: LLM, after_clauses: list[Clause] | None = None) -> list[FunctionMatch]` (внутри при `none` сам зовёт `confirm_loss`; без `after_clauses` второй поиск идёт только по функциям «после») и `confirm_loss(fn: Function, after: list[Function], after_clauses: list[Clause], llm) -> FunctionMatch`. Функции с `modality = prohibition` тебе не передаются (S08 отделяет их в `constraints`); если передали — пропускай. Похожесть (сигнатура, BM25, косинус) статус не ставит никогда; статус ставит только проверка LLM. У каждого `FunctionMatch` — `sources` всех функций обеих сторон (у односторонних — имеющейся), `verified`, `verification` ∈ exact|lexical|llm, `confidence`, `note`.

Сделай:
1. `candidates.py`, лексика: `tokenize(text) -> list[str]` — нижний регистр, ё→е, коды и аббревиатуры (БВА, ДЗО, СВА, «ИТ», номера вида «2.3.») сохраняются как отдельные токены (не режутся и не приводятся к основе), остальные слова — грубая основа (отсечь окончания ≥ 3 букв при длине слова > 5), стоп-слова («и», «в», «на», «по», «с», «для», «о», «об»). `Candidate = dataclass(after_id: str, score: float, reasons: list[str])`, `reasons` ⊂ {"exact", "lexical", "signature", "dense"}. BM25-подобная оценка на чистом Python/numpy (k1 = 1.5, b = 0.75, idf по корпусу «после»), top-5 по каждой функции «до». Точное совпадение нормализованного текста (нижний регистр, ё→е, без пунктуации и лишних пробелов) — кандидат с `reasons = ["exact"]` и `score = inf`, верификатор помечает такую пару `verification = "exact"`. Равенство `Function.signature` — отдельный список кандидатов с `reasons = ["signature"]`, порядок по BM25 внутри группы.
2. `candidates.py`, dense (опционально): `embed(texts: list[str], llm: LLM | None) -> list[np.ndarray | None]` — для каждого текста сначала кэш `backend/app/mocks/embeddings/{sha256(text)}.json` (формат `{"model": "text-embedding-3-small", "text_sha256": ..., "vector": [...]}`); нет в кэше и `llm.mode == "live"` при непустом `llm.settings.openai_api_key` → `llm._get_client().embeddings.create(model="text-embedding-3-small", input=[...])` пакетами ≤ 100, результат пишется в кэш; нет в кэше и режим mock (или ключа нет) → `None`, dense для этой функции пропускается **без ошибки** и без `LLMError`. Косинус — только ранжирование top-5, порог косинуса решением не является (0,85 давал 44 ложных дубля из 150). Слияние трёх рангов (лексический, сигнатура, dense) — RRF: `score = Σ 1/(60 + rank)`; итог top-5 с объединёнными `reasons`. `find_duplicate_candidates`: тот же BM25 + сигнатура + опциональный dense между функциями разных `unit_id`, пары внутри одного подразделения не сравниваются; шаблонные формулировки исключаются до поиска («иные функции», «поручения руководства», «согласно законодательству», «в пределах компетенции» — список `TEMPLATE_PHRASES`).
3. `matching.py`, LLM `verify_matches` — по одному вызову на каждую функцию «до» с непустым списком кандидатов: system — текст `prompts/verify_matches.md` (по-русски: сравнить действие, объект и исполнителя; определения решений: `kept` — та же функция, `changed` — то же действие и объект, изменена формулировка/исполнитель внутри подразделения, `moved` — та же функция у другого подразделения, `split` — одна «до» → несколько «после», `merge` — «после» вобрала эту и другие функции «до», `partial` — совпадает лишь часть действия/объекта, `none` — среди кандидатов нет; «аудит ИТ» и «аудит закупок» — разные объекты, не совпадение; id не выдумывать, цитаты — дословно из переданных пунктов), user — JSON `{before: {id, unit, executor, modality, text, clause_number, section_path, lead_in, context: [{number, text}]}, candidates: [{id, unit, executor, modality, text, clause_number, section_path, lead_in, context: [...]}]}` (≤ 5 кандидатов), schema — `strict_schema` модели `VerifyMatchesOut {decision: kept|changed|moved|split|merge|partial|none, after_ids: list[str], rationale: str, quotes: list[str]}` (если S13 уже влил `llm_schemas.py` — брать оттуда, иначе своя модель с `extra="forbid"`). Проверка кодом: `after_ids` только из переданных кандидатов, чужой id → отбрасывается с `logger.warning`; `decision ∈ {kept, changed, moved, split, merge, partial}` при пустом `after_ids` → ответ невалиден, функция остаётся непроверенной; `quotes` — каждая должна быть подстрокой текста одного из переданных пунктов, иначе отбрасывается. Перевод в `FunctionMatch`: `kept`/`changed`/`moved` → `kind = one_to_one`, тот же `status`; `split` → `kind = split`, `status = changed`, `after` — все `after_ids`; `merge` → `kind = merge`, `status = changed` (несколько «до» с одним `after_id` собираются в один `FunctionMatch` с `before` из всех них); `partial` → `kind = partial`, `status = changed`, в `note` — что не покрыто; `moved` только если `unit_id` действительно другой, иначе понизить до `changed` с `note`. `verified = True`, `verification = "exact"` для кандидата с `reasons == ["exact"]` при `decision = kept`, иначе `"llm"`; `confidence`: exact 1.0, kept/moved 0.9, changed/split/merge 0.8, partial 0.6. Функции «после», не вошедшие ни в одну связь, → `status = new`, `kind = one_to_one`, `before = []`, `verified = True`, `verification = "lexical"`, `note` «у функции нет кандидатов среди «до»», `confidence` 0.7.
4. `matching.py`, потеря — только после проверки по **всему** документу «после». При `decision = none` (или пустом списке кандидатов) вызывай `confirm_loss(fn, after, after_clauses, llm)`: второй лексический поиск (тот же BM25 из `candidates.py`) по всем функциям «после» и по сырому тексту всех пунктов «после» — top-5 ближайших пунктов с номерами; user — JSON `{before: {...как выше}, nearest_functions: [{id, unit, text, clause_number}], nearest_clauses: [{number, text}]}`, system — `prompts/confirm_loss.md` (по-русски: подтвердить, что действие над этим объектом в документе «после» отсутствует; если есть похожий пункт — процитировать его и сказать, чем отличается; номер только из переданных), schema — `ConfirmLossOut {lost: bool, nearest_clause_number: str | None, nearest_quote: str, rationale: str}` (spec §5; из `llm_schemas.py`, если S13 уже влит, иначе своя модель с `extra="forbid"`; `None` — похожего пункта нет). `nearest_clause_number` не из переданных → ответ невалиден. `lost = true` → `FunctionMatch(status = lost, kind = one_to_one, after = [], verified = True, verification = "llm", confidence 0.85, note = rationale + ближайший пункт)`. Во всех остальных случаях (ответа нет — `LLMError`, невалидный ответ, `lost = false` без найденной пары, превышен лимит вызовов `MAX_VERIFY_CALLS = 400` на прогон) — функция остаётся **кандидатом в потери**: `status = lost`, `verified = False`, `verification = "lexical"`, `confidence` 0.4, `note` с причиной («нет ответа проверки», «лимит пакета», «низкая уверенность: ближайший пункт N.N»). Не выдумывать `lost` как вывод: S08 считает `stats.unverified_candidates` по `verified = False`, UI показывает их отдельно «требует проверки».
5. Mock-режим: при `llm.mode == "mock"` `verify_matches` и `confirm_loss` читают `mocks/<имя вызова>/<hash>.json`, `hash = sha256(json.dumps(user_payload, ensure_ascii=False, sort_keys=True))[:16]`; нет файла — `LLMError` с именем ожидаемого файла, не пустой ответ (для функции «до» это означает «нет ответа проверки» → `verified = False`, прогон не падает). Пустые кандидаты — `verify_matches` не вызывать, сразу `confirm_loss`. Фикстуры для случаев из теста — в формате живого ответа, чтобы S15 заменил их реальными без правки кода. `mocks/embeddings/` — создай каталог с `README.md` (что здесь и формат файла), без векторов: в тесте dense пропускается.
6. `tests/test_matching.py` (без ключа, `LLM_MODE=mock`): `Function` и `Clause` собирай руками с `Source` (пункты вида «2.3.», цитаты — из `data/case11/*.txt`). Проверь: (а) коллизия сигнатуры — «проводит аудит ИТ-систем» «до» и «проводит аудит закупок» «после» имеют одинаковую `signature`, попадают в кандидаты, но `verify_matches` с фикстурой `none` НЕ даёт `kept`/`changed`; без фикстуры `confirm_loss` — `verified = False`; (б) split — одна функция «до» → две «после» с фикстурой `split` даёт один `FunctionMatch` с `kind = split`, `len(after) == 2`, `verified = True`; (в) функция, отсутствующая после, получает `status = lost, verified = True` только при фикстуре `confirm_loss` с `lost = true` и `nearest_clause_number` из переданных; без фикстуры — `status = lost, verified = False` и `note` с причиной; (г) точное совпадение текста → `verification = "exact"`, `confidence = 1.0`; (д) чужой `after_id` из фикстуры отбрасывается; `nearest_clause_number` не из переданных → `verified = False`; (е) `find_candidates` возвращает ≤ 5 кандидатов на функцию, токен «БВА» не режется, в mock без кэша dense не падает; (ж) каждая функция «до» и «после» встречается ровно в одном `FunctionMatch`; у каждого — непустые `sources` на имеющейся стороне; пустые списки → пустой результат без вызова LLM; `find_duplicate_candidates` не даёт пар внутри одного подразделения и отбрасывает «иные функции».

## Дополнение по аудиту: содержание и назначение проверяются раздельно

- Одинаковый текст пункта не даёт `kept` автоматически: сначала проверяется, совпал ли исполнитель (через карту соответствия подразделений из `app/units.py`), модальность и `lead_in`. Одинаковая строка под другим родительским запретом («не имеют права:») — не сохранённая обязанность. Одинаковый текст у другого исполнителя — `moved` (если подразделения не сопоставлены как одно и то же) с `verification="exact"` только по содержанию и пометкой изменения владельца.
- Изменение содержания (текст) и изменение назначения (исполнитель/подразделение) — два независимых признака в `note`: «содержание: сохранено/изменено; назначение: сохранено/перенесено».
- Поиск кандидатов всегда идёт по ВСЕМУ противоположному комплекту (все подразделения), в обе стороны (до→после и после→до); `new` присваивается только функциям «после», не найденным при обратном поиске.
