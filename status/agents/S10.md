## Файлы

- `backend/app/candidates.py` — P4a, только кандидаты, без статусов:
  - `tokenize` (коды/аббревиатуры БВА, ДЗО, СВА, ИТ и номера «2.3.» остаются токенами как есть, остальные слова — грубая основа, стоп-слова убираются), `normalize_text`;
  - `BM25` на numpy (k1 = 1.5, b = 0.75, idf по корпусу поиска);
  - ранг по `Function.signature` (внутри группы порядок по BM25);
  - `embed(texts, llm)` — кэш `mocks/embeddings/{sha256}.json` → в live с ключом `embeddings.create` пакетами ≤ 100 с записью в кэш → иначе `None` без ошибки;
  - RRF `Σ 1/(60 + rank)`, точное совпадение — `Candidate(reasons=["exact"], score=inf)` первым;
  - `find_candidates(before, after, llm=None, k=5)`, `rank_candidates` (им же идёт обратный поиск);
  - `find_duplicate_candidates(functions, k=5, llm=None)` — пары только между разными `unit_id` одной версии, `TEMPLATE_PHRASES` снимаются до поиска, чисто шаблонные функции («иные функции», «прочие поручения Главного аудитора») в поиск не идут; третий элемент кортежа — похожесть 0..1 (Жаккар по токенам, 1.0 при дословном совпадении): только для показа, не решение.
- `backend/app/matching.py` — P4b, решение:
  - `verify_matches(before, after, candidates, llm, after_clauses=None, *, before_clauses=None, unit_changes=None)` и `confirm_loss(fn, after, after_clauses, llm, *, ...)` — позиционная часть совпадает с вызовом из `pipeline.py` S08;
  - дословный текст сам по себе не даёт `kept`: код сверяет модальность (функции и пункта), `lead_in` и владельца (карта `unit_changes` S05, иначе `executor`). Тот же владелец → `kept`, `exact`, 1.0; другое подразделение по карте → `moved`, `exact` по содержанию, 0.9, в `note` написан перенос. Всё остальное идёт в LLM;
  - `verify_matches` (LLM, strict-схема `VerifyMatchesOut`): `after_ids` только из переданных (чужие отбрасываются с `logger.warning`), цитаты должны быть подстроками переданных пунктов, `moved` при том же подразделении понижается до `changed`, `kept`/`changed` при подразделении, другом по карте, становятся `moved`;
  - связи один-ко-многим: компоненты связности подтверждённых связей → один `FunctionMatch` на компоненту (`split`, `merge`, в том числе многие-ко-многим, `partial`), каждая функция — ровно в одном `FunctionMatch`;
  - `none` или пустые кандидаты → `confirm_loss`: второй BM25 по всем функциям и по сырым пунктам «после», LLM (`ConfirmLossOut`), номер пункта только из переданных. `lost = true` → `verified = True`, 0.85. Нет ответа, невалидный ответ, `lost = false` или лимит `MAX_VERIFY_CALLS = 400` → `status = lost, verified = False, verification = lexical`, 0.4, в `note` причина;
  - обратный поиск после→до: функция «после» добавляется в список кандидатов своей ближайшей «до». Она становится `new, verified = True`, если обратный поиск ничего не нашёл (`lexical`) или ближайшая «до» проверена и связь не подтвердила (`llm`). В остальных случаях это «кандидат в новые», `verified = False`;
  - в `note` каждой связи — «содержание: сохранено/изменено/разделено…; назначение: сохранено/перенесено/передано преобразованному подразделению/изменён исполнитель» + rationale модели;
  - mock: `mocks/<вызов>/<sha256(payload)[:16]>.json`, нет файла → `LLMError` с именем файла → «нет ответа проверки», прогон не падает. Live с `LLM_RECORD_MOCKS=1` пишет ответы модели в те же файлы (как в `units.py`).
- `backend/app/prompts/verify_matches.md`, `backend/app/prompts/confirm_loss.md` — по-русски: действие / объект / исполнитель, «аудит ИТ» ≠ «аудит закупок», id и номера не выдумывать, цитаты дословно.
- `backend/app/mocks/verify_matches/*.json` (4), `backend/app/mocks/confirm_loss/*.json` (2) — формат живого ответа модели, под сценарии теста.
- `backend/app/mocks/embeddings/README.md` — назначение и формат кэша, векторов нет.
- `backend/tests/test_matching.py` — 17 тестов на реальных пунктах редакций 8/9: 2.4.15 дословно → `kept/exact/1.0`; 5.3.3 → 5.3.2.а (ДИТААД) + 5.3.2.б (ДОА) → `split`; 5.6.5 ДККМ → 5.6.3 «Директоры департаментов» → `moved/exact`; 5.3.11 → 5.3.12 с выдуманным id в фикстуре → `changed`, id отброшен; 5.6.3 «внешняя оценка» → потеря, подтверждённая `confirm_loss` с ближайшим 11.5; плюс синтетическая коллизия сигнатуры, пустые входы, лимит вызовов, dense из временного кэша, кандидаты дублей.

## Что не сделано / для интегратора

- **S08 (`pipeline.py`)**: чтобы работали `moved` по карте подразделений и контекст функций «до», в вызов `verify_matches` нужно добавить `before_clauses=[c for d in run.docs["before"] for c in d.clauses]` и `unit_changes=run.unit_changes`. Без них всё работает, но `lead_in`/`section_path` «до» пусты, а владелец сверяется только по `executor`: дословные пары с разным исполнителем уходят в LLM.
- В S08 `find_duplicate_candidates(run.functions["after"])` вызывается без `llm`, поэтому dense для дублей берётся только из кэша. Это нормально.
- `llm_schemas.py` (S13) в ветке ещё нет: `VerifyMatchesOut`/`ConfirmLossOut` объявлены в `matching.py` с `extra="forbid"`. Если S13 уже влит, они импортируются из `app.llm_schemas`. `nearest_clause_number: str | None` (соглашение 14:25).
- Фикстуры тестового комплекта целиком (реальный прогон ред. 8 → 9) — задача S15: живой прогон с `LLM_RECORD_MOCKS=1` запишет их в те же каталоги без правки кода. Пока в mock-режиме на комплекте потери и новые функции без фикстуры честно остаются «требует проверки».
- Пара из промпта «проводит аудит ИТ-систем» / «проводит аудит закупок» при текущем `lib_normalize.signature` даёт РАЗНЫЕ сигнатуры (`…|ит-систем` против `…|закупок`). Поэтому тест коллизии взял формулировку, на которой коллизия настоящая: «проводит аудит, в том числе ИТ-систем Общества» / «…закупок Общества» → обе `КОНТРОЛИРОВАТЬ|аудит`. Тест проверяет равенство сигнатур явно.
- Cut-if не понадобились: dense с вызовом embeddings, `merge`/`partial` и второй поиск по сырым пунктам сделаны.
